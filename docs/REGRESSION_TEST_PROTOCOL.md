# Протокол защиты регрессионных тестов

Утверждён пользователем. Цель: не потерять функциональность и не скрыть
регрессию изменением теста, фикстуры, фильтра или исходного baseline.

**Существующие регрессионные тесты — защищённый контракт. Новые oracle-тесты
не заменяют его и не компенсируют падения исходного набора.**

## 1. Существующие тесты заморожены

По умолчанию разрешено только добавлять новые тесты в новых файлах.

Без отдельного разрешения пользователя запрещены:

- изменение SQL, входных данных, ожидаемых результатов и исключений;
- изменение способа чтения результата, например `string` → `byte[]`;
- удаление, переименование или ослабление проверок;
- добавление `Skip`, `BlockedByPort`, фильтров и других способов исключить
  падение;
- изменение фикстур и общих помощников, влияющих на старые тесты.

Это относится и к тестам, которые агент считает устаревшими или неправильными.

## 2. Перед работой фиксируется baseline

На исходном коммите сохраняются:

- коммит порта и версия/контрольная сумма эталонного jar;
- точные команды запуска;
- список тестов с исходами `Passed / Failed / Skipped`;
- TRX-отчёты;
- контрольные суммы существующих тестовых файлов и фикстур.

Baseline нельзя автоматически обновлять под текущий результат. Его смена —
отдельное согласованное действие.

## 3. Результаты сравниваются по именам тестов

Одних счётчиков недостаточно: пять новых зелёных тестов могут скрыть пять
старых красных.

После изменения строится отчёт:

| Переход | Значение |
|---|---|
| `Passed → Failed` | Новая регрессия; блокирует завершение |
| `Passed → Skipped / не запущен / удалён` | Потеря проверки; блокирует завершение |
| `Failed → Passed` | Исправление; подтверждается эталоном |
| `Failed → Failed` | Старый дефект; отдельно показывается изменение причины |
| Новый тест | Отдельный результат |

Новые oracle-тесты не компенсируют падение старых.

## 4. Каждый новый провал разбирается до изменения теста

Для каждого провала агент предоставляет:

1. Имя теста и точную проверку.
2. Исходный и текущий результат порта.
3. Результат того же SQL/операции на эталонном jar.
4. Причины расхождения и предлагаемую правку.

Нельзя проверять другой SQL, другой тип получения значения или только
успешную часть сценария и на этом основании объявлять тест неверным.

Если старый тест требует `TODOException`, а функция теперь реализована, это
конфликт контракта теста с переносом, требующий решения пользователя.
Самостоятельно заменять проверку нельзя.

## 5. Изменение старого теста утверждается отдельно

Сначала агент показывает точный diff, доказательство из jar и объяснение,
какую гарантию сохраняет новая проверка.

Разрешение пользователя относится к этому конкретному изменению. Команды
«выполняй спринт» или «исправляй функции» не являются разрешением менять тесты.

Утверждённые изменения тестов идут отдельным коммитом, чтобы их можно было
проверить и откатить независимо от реализации. Сам коммит выполняется только
по явной команде пользователя.

## 6. Автоматический контроль перед завершением

Требуется автоматическая проверка, которая:

- обнаруживает изменения старых тестов и фикстур;
- допускает только явно утверждённые изменения;
- сравнивает исходы тестов с baseline;
- блокирует завершение при новых регрессиях, пропавших проверках или
  неполном прогоне.

Итоговый отчёт всегда содержит отдельно:

- результат исходного регрессионного набора;
- новые тесты;
- conformance;
- утверждённые изменения тестов;
- незакрытые падения.

## 7. Применение к текущему Batch A

При утверждении протокола старые тесты восстановлены. Незакрыты:

- три регрессионных падения;
- девять JSON-conformance падений.

Они разбираются по этому протоколу. До их разрешения спринт не объявляется
зелёным или принятым.
