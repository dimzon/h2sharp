# ADR-001: .NET-точки расширения и необязательные провайдеры

**Статус: принято пользователем.** Решение принято при обсуждении HASH,
плагинов и DI 2026-10-25. **Реализация extension-спринта отложена**, само
архитектурное решение уже действует и не является кандидатом.

Связанные решения: D-020 и D-021 в
[APPROVED_DEVIATIONS.md](APPROVED_DEVIATIONS.md).
План внедрения: [SPRINT_DOTNET_EXTENSIONS.md](SPRINT_DOTNET_EXTENSIONS.md).

## Контекст

H2Sharp переносит SQL H2 2.5 на .NET. Использование .NET-криптографии,
dependency injection и .NET UDF требует платформенных API, которых нет
в исходниках org.h2. Их отсутствие в Java не делает их дефектом порта:
пользователь явно выбрал эту архитектуру.

## Принятое решение

### 0. H2Connection — основная точка настройки

Уточнение пользователя: конфигурация расширений задаётся методами семейства
`RegisterXXXX()` через эксплицитно реализованный интерфейс H2Connection,
по примеру IH2Test. В обычном IntelliSense connection/command методы
регистрации не появляются. Главная точка настройки остаётся connection;
конкретное имя регистрационного интерфейса определяется в спринте. Порядок использования:
**создали connection → зарегистрировали обработчики/фабрики → Open()**.

- Регистрация разрешена только при `ConnectionState.Closed` и до Dispose.
  На Open/Connecting/Broken и иных состояниях она явно отказывает.
- Open создаёт runtime-состояние из подготовленной конфигурации. Активная
  сессия не перенастраивается скрытым изменением registry.
- Хэш-фабрики имеют тип `Func<HashAlgorithm>`; UDF, alias, trigger и diagnostics
  регистрируются через соответствующие connection-level методы.
- DI/fluent builder/data source/NuGet startup integration — отдельные надстройки
  над этим API, не конкурирующие точки конфигурации. Прямое использование
  connection не требует DI-контейнера.
- `IH2Test` — существующий пример передачи настроек до Open и эксплицитного
  интерфейса. Производственная регистрация имеет отдельный интерфейс,
  не помещается в IH2Test; его текущие test seams сохраняются.

Точные сигнатуры RegisterXXXX реализуются в extension-спринте. Регистрационные
описания обработчиков и schema-объекты SQL имеют разные сроки жизни: при общей
именованной базе и нескольких соединениях необходимо проверить изоляцию/
совместимость конфигурации и сохранение FunctionAlias/Trigger metadata.

Уточнение пользователя: максимально используются стандартные BCL-типы и
типизированные `Func<...>`, без собственных публичных delegate/interface
обёрток для обычной регистрации UDF. Семейство API:

```csharp
RegisterUdf<TResult>(string name, Func<TResult> implementation);
RegisterUdf<TArgument, TResult>(string name, Func<TArgument, TResult> implementation);
RegisterUdf<T1, T2, TResult>(string name, Func<T1, T2, TResult> implementation);
// Далее обычные Func-перегрузки нужной арности.
RegisterHashAlgorithm(string name, Func<HashAlgorithm> factory);
```

`Func<TResult>` здесь — вызываемая SQL-функция без аргументов, не фабрика
обработчика. DI/instance creation вынесены в надстройку с явно отличимым
контрактом фабрики; они в итоге используют те же RegisterXXXX.
Перегрузки UDF — тонкие оболочки над единым механизмом регистрации. BCL
Delegate/MethodInfo могут быть внутренней основой для валидации metadata и
редких сигнатур; reflection не выполняется заново на каждой строке.

CLR-типы аргументов/результата определяют проверяемые SQL-типы, nullable/NULL
mapping и число параметров. Метаданные determinism/read-only не угадываются
из типа Func и не заменяют отдельный SQL-контракт H2.

### 1. Криптографические примитивы

- Единая точка выбора хэш-алгоритма в движке — словарь
  **имя → `Func<System.Security.Cryptography.HashAlgorithm>`**.
- Фабрика создаёт новый stateful HashAlgorithm для операции. Публичный
  контракт — стандартный .NET тип, не особое имя внутреннего адаптера.
- Адаптеры к примитивам допустимы в отдельном .NET-пространстве имён.
  Их реализация — внутренняя часть провайдера; общий API HashAlgorithm
  обеспечивает ComputeHash/streaming/Initialize/reuse/Dispose.
- BCL-примитивы — основа ядра. Недостающие/внешние алгоритмы подключаются
  необязательными NuGet-провайдерами через те же фабрики.
- Отсутствующий провайдер даёт явную ошибку с указанием способа подключения;
  не подменяется другим digest, пустым значением или встроенной самописной
  реализацией. Ручной перенос crypto-примитивов заменён этим выбором.

### 2. Общие .NET UDF и SQL aliases

- Предусмотрен общий механизм произвольных UDF на .NET: делегаты, static
  методы и instance methods объектов, созданных DI.
- SQL aliases подключаются к тому же механизму. Разрешены необходимые
  платформенные регистрационные API и адаптеры вызова .NET-кода.
- SQL-метаданные и выполнение продолжают использовать Schema/DbObject и
  Expression/Prepared H2. Не вводится конкурирующее SQL-дерево/реестр схем.
- Преобразования Value, NULL, типы результата, determinism, overload/arity
  и metadata persistence должны быть проверены отдельно. DI не даёт права
  молча менять эти SQL-контракты.

Обычные вызовы вида `FunctionName(arg, arg, ...)`, включая builtins, проходят
общий readParameters и диспетчер на данных registry. Добавление реализации
дополняет factory/metadata данные, а не требует новой ветви parser. Factory
создаёт соответствующее эталонное Expression/Prepared; конкурирующего AST нет.
Специальная грамматика (EXTRACT ... FROM, TRIM ... FROM, JSON KEY/VALUE,
агрегатные FILTER/WITHIN GROUP/OVER) сохраняет эталонные читатели. Schema names,
приоритет aliases/builtins, arity и cache invalidation сохраняют правила H2 2.5.

UUID-генерация предусмотрена как заменяемая .NET UDF с default-реализацией.
Обычная база работает без ручной регистрации; внешний provider заменяет
реализацию через тот же pre-Open API. SQL-имена, версии UUID и недетерминированность
H2 сохраняются. IH2Test UUID seam подключается к общему механизму без потери
контракта тестов.

### 3. DI, triggers и diagnostics

- DI используется для создания обработчиков UDF, triggers и trace/diagnostics
  и управления их жизненным циклом. Допустимы IServiceProvider-точки
  подключения и отдельные удобные DI-пакеты.
- DI-надстройка конфигурирует закрытый H2Connection через RegisterXXXX;
  connection-level API остаётся основной точкой настройки.
- Области жизни независимых баз/data source и connection/command должны
  быть изолированы; scope и IDisposable обрабатываются явно.
- Trigger/FunctionAlias/TraceSystem lifecycle и транзакционные точки вызова
  берутся из H2 2.5. DI не заменяет выполнение SQL разбором текста callback-ами.
- Конкретный logging framework и сторонняя криптобиблиотека не становятся
  обязательными зависимостями ядра.

### 4. ORA_HASH

- ORA_HASH находится вне основного implementation scope и поставляется
  будущим необязательным пакетом как обычная UDF на общем API.
- Его bucket/seed/BIGINT-контракт не подменяет интерфейс HashAlgorithm.
  Digest-фабрика и SQL UDF — разные предусмотренные точки расширения.
- Исходные тесты сохраняются. До появления реализации функция явно
  отказывает и не маскируется исключением из набора.

## Правило сохранения решения и кода

**Нельзя удалять, заменять заглушкой или переписывать соответствующий этому
ADR код только потому, что «в Java-оригинале иначе» или «у класса/метода
нет аналога в org.h2».** Платформенные фабрики, адаптеры, DI API и plugin/UDF
точки расширения в указанной области — утверждённое решение, а не случайное
отступление. Их .NET-имена сами по себе не требуют устранения.

Перед таким рефакторингом агент обязан проверить этот ADR, D-020/D-021,
спринт и применимость решения к коду. Дефект конкретной реализации
исправляется с сохранением принятой границы. Пересмотр самой архитектуры,
удаление соответствующего ей API или возврат к иной модели требует
**отдельного явного решения пользователя**.

Отложенный статус спринта не отменяет ADR и не является основанием
удалить уже сделанный соответствующий код. План определяет очередность
внедрения; ADR определяет обязательную архитектурную границу.

## Пределы решения

ADR не разрешает собственный SQL parser/AST, реестр таблиц вместо Schema,
новые правила cache invalidation, ложные заглушки или ослабление тестов.
Чтение эталона H2 2.5 и oracle обязательны для соответствующих SQL-контрактов.
Новые отклонения вне этого ADR требуют визы пользователя по обычным правилам.

Точный публичный API, имена/поставка наших NuGet-пакетов и способ startup
registration реализуются и проверяются по extension-спринту. Плановые
названия пакетов не означают, что пакет уже опубликован или подключён.
