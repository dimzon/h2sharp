# Перечень утверждённых отклонений от эталона (H2 2.5.x)

## A. Утверждены

### D-001. Синтаксис регулярных выражений — .NET

Для `REGEXP`, `~`, `~*`, `!~`, `!~*` и regex-функций используется
`System.Text.RegularExpressions`, без переноса движка `java.util.regex` и без
перевода Java-шаблонов. Основание: принятое проектное решение (AGENTS.md).

Уточнение пользователя при B5: SQL pattern передаётся BCL **без изменений**.
Запрещено вставлять конструкции в pattern, переписывать группы, anchors/escapes
или препроцессить шаблон ради совпадения с Java. SQL-флаги отображаются в
RegexOptions отдельно. Отличия движков фиксируются явно, без трансляторов.

### D-002. Без коллатора

`SET COLLATION <имя>` отказывает (`NotSupportedException`). Замеры против
эталона в `MIGRATION_STATUS.md`: веса .NET не воспроизводят CLDR root.
Пересмотр: ORDER BY с локалью, персистентная зависимость, чтение данных Java-H2.

### D-003. Только встроенный режим, без сети

Движок выполняется в процессе приложения; TCP/remote вне скоупа.
Файловое хранение **в скоупе** и реализовано: открытие/закрытие `.mv.db`, формат
эталона в обе стороны, словарь схемы (`SYS`). Не портированы только `.lock.db`
(`FILE_LOCK=FILE|SOCKET`) и `DB_CLOSE_ON_EXIT`; URL с такими значениями
`FILE_LOCK` и с `AUTO_SERVER=TRUE` отвергается (`TODOException`/50100), а не
молча работает как FS.

### D-004. Ролей/пользователей нет

Пользователей и паролей в connection string нет. Сессия имеет фиксированный
principal `"sa"`: `CURRENT_USER`/`SESSION_USER`/`SYSTEM_USER`/`USER` возвращают
`"sa"`, `CURRENT_ROLE` — константа `'PUBLIC'` (`PublicRoleName`), `checkAdmin` —
no-op; principal имеет полный доступ. Ключи `USER`/`PASSWORD`/`User ID`/
`Password` в connection string отвергаются, а не игнорируются.
`SET PASSWORD` / `SET SALT` — отказ `TODOException` (нужны AlterUser и
пользователи). Пересмотр — только вместе с пользователями.

### D-005. Работы с CSV и файлами нет — вне scope

`CSVREAD`/`CSVWRITE`/`FILE_READ`/`FILE_WRITE` не реализуются: для
встраиваемого движка файловый CSV I/O признан ненужным. Это утверждённое
пользователем отклонение от H2 2.5, а не дефект; соответствующие conformance-
тесты помечены `BlockedByPort` и остаются маркером решения. EF Core и linq2db
эти функции не используют. Пересмотр — только по отдельному указанию
пользователя.

### D-006. Фасад Dialect и расширение видимости ValueLob

У `Data/Dialect.cs` нет аналога в `org.h2`; `ValueLob.LobOctetLength`,
`ValueLob.LobCharLength` и `FormatLobDataComment` расширены с protected до
internal. Задокументировано в шапке файла и в MIGRATION_STATUS.md.

### D-007. `CURRENT_ROLE` — константа `'PUBLIC'`

Замер T14 на пустой БД; пересмотреть при появлении ролей.

### D-008. `CANCEL_SESSION` отказывает, а не отвечает TRUE

Эталон отменяет выполняемую команду сессии. Порт выполняет команды
синхронно и текущей команды не отслеживает, поэтому `CANCEL_SESSION` для
найденной сессии вызывает `SessionLocal.Cancel()`, который отказывает
`TODOException`. Утверждено пользователем (P-002 = вариант «вызывать Cancel»).
Пересмотр — при появлении отмены команд.

### D-009. `DATABASE_PATH` делегирует базе

`SysInfoFunction` спрашивает `Database.GetDatabasePath()`, как эталон.
Для in-memory ответ `null`; для persistent — `FileUtils.ToRealPath`, как в
эталоне (проверено `DatabasePathMatchesTheReference`).

### D-010. `MEMORY_FREE` / `MEMORY_USED` не отвечают

Эталон читает `Runtime.freeMemory()`/`totalMemory()`. Платформа не
предоставляет семантику кучи JVM (`GC.GetGCMemoryInfo` отвечает на другой
вопрос), поэтому ветви бросают `TODOException`; тесты — в `BlockedByPort`.
Утверждено пользователем (P-003).

### D-011. Словарь схемы: таблица как отдельный вход, пропуск USER-строк

В эталоне таблица — `DbObject`, поэтому у `addMeta`/`populateRowFromDBObject`
один вход. В порте `Tables.Table` не `DbObject`, поэтому добавлены
`Database.AddMeta(SessionLocal, Table)` и `MetaRecord.PopulateRowFromTable` с той
же строкой (ID/HEAD/TYPE/SQL, тип `TABLE_OR_VIEW`). Строки `USER`
(в файле эталона всегда есть встроенный пользователь) парсер порта не читает:
пользователей нет (D-004). Эталон при старте без listener тоже не прерывает
открытие на ошибке строки, а пишет её в trace; trace в порте нет, поэтому
пропуск не оставляет сообщения. `LockMeta`/`UnlockMeta` — no-op: менеджер
блокировок не портирован. Утверждено пользователем.

### D-012. XMLCOMMENT — стандартная обработка BCL (решение для будущего переноса)

Основание: пользователь утвердил результат XML-макета 2026-10-25:
принимаем стандартное исправление `XmlWriter.WriteComment`, включая
`x--y` → `x- -y` и добавление пробела после конечного дефиса. Собственный
санитайзер не вводится. Преобразование `--` совпадает с `StringUtils.xmlComment`
H2 2.5; формат комментария берётся у BCL, без добавляемой H2 рамки пробелов
и отступов. Входные значимые пробелы не обрезаются.

Статус: реализовано в XMLFunction и проверено SQL/ADO.NET. Исправления
проверяются по узлу Comment и точному ожидаемому
содержимому; эталонная рамка проверяется отдельно, без Trim и без удаления
комментариев из C14N. Исходные тесты этим решением не изменяются.
Нормализация CRLF/CR согласована отдельно в D-013, выбор Indent — в D-014.
Приоритет xml:space согласован в D-015, фрагментный namespace-контекст — в D-016.

### D-013. XMLCOMMENT и XMLCDATA — нормализация переводов строк XML 1.0

Основание: пользователь утвердил результат макета 2026-10-25: принимаем
обычную нормализацию литеральных переводов строк при XML-разборе содержимого
Comment и CDATA. CRLF и одиночный CR читаются как LF; LF сохраняется.
Это делает System.Xml.XmlReader по XML 1.0, без собственного нормализатора.

Решение относится к прочитанному XML-содержимому, а не требует переписывать
возвращаемую SQL-строку или удалять её пробелы. Проверяются точное содержимое
после разбора и тип узла Comment/CDATA. TAB, обычные пробелы и NEL (U+0085)
сохраняются; правила XML 1.1 не подставляются вместо XML 1.0.

Статус: реализовано в XMLFunction и проверено SQL/ADO.NET. Изменения XMLTEXT,
XMLATTR, Indent и namespace-контекста этим решением не утверждены. Случай `]]>`
согласован отдельно в D-017.
Исходные регрессионные тесты не изменяются; прежние строгие сравнения кодовых
единиц макета сохраняются отдельно от проверок согласованного XML-содержимого.

### D-014. XMLNODE — без форматирования по умолчанию, явный TRUE включает Indent

Основание: пользователь утвердил результат макета 2026-10-25: при отсутствии
четвёртого аргумента XMLNODE использует `Indent=false`; явный `FALSE` также
отключает форматирование, явный `TRUE` включает стандартное форматирование BCL.
Явный SQL NULL по-прежнему даёт SQL NULL. Существующие пробелы и переводы строк
содержимого не удаляются, чтобы получить «неформатированный» результат.

Эталон H2 2.5 задаёт `indent=true` по умолчанию и форматирует содержимое,
когда оно содержит LF. Отличие от эталона принято явно: обычный вызов не
добавляет текстовые пробелы. Для явного TRUE используется алгоритм BCL,
который может добавить текстовые узлы; эти изменения видны в строгих сравнениях.

Статус: реализовано в XMLFunction и SQL-разборе H2 2.5.
Исходные регрессионные тесты не изменяются без отдельного утверждения. Приоритет
`xml:space='preserve'` согласован в D-015; отложенный namespace-контекст — в D-016.

### D-015. XMLNODE — xml:space="preserve" отключает Indent для всего результата

Основание: пользователь утвердил консервативное правило 2026-10-25: если
создаваемый элемент или любой элемент его содержимого имеет
`xml:space="preserve"`, форматирование всего XMLNODE отключается, даже при
явном TRUE. Вложенный `xml:space="default"` не отменяет этот глобальный запрет.
При отсутствии preserve обычный default сам по себе форматирование не отключает.

Ищется реальный атрибут в XML namespace
`http://www.w3.org/XML/1998/namespace`, средствами BCL XPath/XmlNamespaceManager.
Обычный `space="preserve"`, атрибут другого namespace и текст комментария с
`xml:space` не являются директивой. Собственного обхода дерева или форматтера нет.

Статус: реализовано в XMLFunction. Проверяются целое XML-дерево, отсутствие новых
пробелов как внутри preserve, так и снаружи, и сохранение исходного LF/текста.
Эталон H2 2.5 не анализирует эту директиву перед своей строковой индентацией;
отличие принято явно. Исходные регрессионные тесты не изменяются.

### D-016. XMLNODE — фрагменты с отложенным namespace-контекстом

Основание: пользователь утвердил фрагментный контракт 2026-10-25: элемент
или атрибут может использовать QName-префикс, который объявится на будущем
родителе. XMLNODE не требует самостоятельного namespace-объявления в каждом
вложенном вызове. Это сохраняет принимаемые H2 2.5 композиции.

Структуру фрагмента проверяет namespace-disabled XmlTextReader; компоненты
QName — XmlConvert, области и наличие привязок — XmlNamespaceManager BCL.
Локальные объявления проверяются namespace-aware средствами BCL. Когда
контекст достаточен, итоговый XML разбирается namespace-aware reader; он также
проверяет дубли атрибутов по расширенным именам. Фиктивных URI и своего реестра
namespace нет. Неразрешённый префикс помечается как требующий контекста,
а не выдаётся за самостоятельно namespace-корректный документ.

До появления контекста QName сохраняет namespace-disabled writer BCL.
Перенос данных через reader/writer сохраняет символы и атрибутные TAB/CR/LF
через стандартные BCL-операции. D-014/D-015 продолжают действовать, включая
xml:space на фрагменте с ещё неразрешённым префиксом. Статус: реализовано
в XMLFunction; исходные регрессионные тесты не изменяются без отдельной визы.

### D-017. XMLCDATA — BCL разбивает `]]>` на несколько CDATA-секций

Основание: пользователь утвердил результат макета 2026-10-25: XMLCDATA
делегирует `XmlWriter.WriteCData`; при `]]>` создаётся несколько CDATA-секций,
конкатенация их прочитанного содержимого сохраняет данные (с D-013 для CR/LF).
Своя замена `]]>` или санитайзер не вводится.

H2 2.5 `StringUtils.xmlCData` при этой последовательности возвращает
экранированный текст. Отличие по типу узлов принято явно: BCL сохраняет CDATA.
Проверяются точный текст, количество/типы секций, повторяющиеся и граничные
последовательности, пробелы, Unicode и композиция с XMLNODE/namespace.
Одна C14N не заменяет эти проверки, поскольку она стирает тип CDATA.

Статус: реализовано в XMLFunction и проверено SQL/ADO.NET. Исходные регрессионные тесты
и эталонные результаты не изменяются; поведение jar проверяется отдельно как текст.

### D-018. XMLSTARTDOC — Unicode-строка без encoding

Основание: пользователь подтвердил 2026-10-25 разделение символов и байтов:
XMLSTARTDOC возвращает Unicode-строку `<?xml version="1.0"?>`, без encoding
и standalone. Декларацию создаёт BCL XmlDocument.CreateXmlDeclaration.
Внутреннее UTF-16 представление .NET string не задаёт кодировку будущего XML-файла.

Это совпадает с декларацией H2 2.5 (его конечный LF — формат вывода).
При превращении XML в байты кодировку выбирает потребитель/stream writer.
Если байтовый XmlWriter указывает encoding, он должен соответствовать реальным
байтам. Для UTF-8 без encoding действует XML-default; UTF-16 проверяется с BOM.

Статус: реализовано в XMLFunction. Декларация проверяется по типу узла,
версии, отсутствию encoding/standalone и чтению UTF-8/UTF-16 потоков. C14N не
заменяет эти проверки: она удаляет декларацию. Исходные тесты не изменяются.

### D-019. REGEXP_REPLACE — replacement в .NET-синтаксисе, без преобразований

Основание: пользователь при B5 выбрал **«.NET как есть»** для отдельного
replacement-аргумента. Pattern по D-001 и replacement передаются стандартной
библиотеке без препроцессинга. Используются Regex.Replace/Match.Result; не
вводится перевод `$1`/`\1`, собственный parser replacement или MatchEvaluator
ради воспроизведения Java. `$1`, `${name}`, `$$`, `$&` и остальные конструкции
имеют стандартное .NET-поведение; `\1` остаётся буквальным текстом.

Java/H2 mode.regexpReplaceBackslashReferences не переопределяет этот контракт;
зависимый от него перевод replacement не переносится. SQL-разбор, количество
аргументов, NULL, flags и PostgreSQL global/default-first следуют H2 2.5.
Отличия matching/позиционных API BCL фиксируются в отчёте, без переделки pattern.

### D-020. Хэши — .NET HashAlgorithm и необязательные провайдеры

Обязательное архитектурное основание и правило сохранения кода:
[ADR-001](ADR_DOTNET_EXTENSIONS.md). Отсутствие .NET API в Java не разрешает
удалить соответствующий этому решению адаптер/фабрику/точку подключения.

Указание пользователя: единая точка выбора алгоритма в движке — словарь
имя → `Func<System.Security.Cryptography.HashAlgorithm>`. Фабрики возвращают
стандартный .NET тип, внутренний адаптер не является публичным контрактом.
Дополнительные алгоритмы поставляются optional NuGet-провайдерами; отсутствие
провайдера даёт явную ошибку с инструкцией подключения, не другой digest.
Ручной перенос отсутствующих crypto-примитивов заменён этим решением.

Регистрация внешних hashes, DI/UDF/aliases/triggers/trace спланирована отдельно
в `docs/SPRINT_DOTNET_EXTENSIONS.md` и по указанию пользователя отложена до
продолжения текущих conformance-задач. Ядро не зависит от BouncyCastle/HashLib.

### D-021. ORA_HASH — optional UDF, реализация вне основного scope

Архитектурное основание: [ADR-001](ADR_DOTNET_EXTENSIONS.md); общие .NET
UDF/aliases/DI/triggers/trace являются принятой .NET-границей (спринт отложен).

Пользователь вывел ORA_HASH в будущий плагин. Он будет обычной .NET UDF на
общем механизме FunctionAlias/DI из `docs/SPRINT_DOTNET_EXTENSIONS.md`.
Встроенная SHA-1 доступна BCL, но bucket/seed/BIGINT-обёртка ORA_HASH находится
в UDF-пакете. До его реализации вызов явно отказывает; исходные conformance
тесты сохраняются как перечень отложенной работы и не исключаются без визы.

### D-022. Криптография — отдельный опциональный пакет H2Sharp.Crypto

Указание пользователя: все криптофункции с обычным синтаксисом
`FunctionName(arg, ...)` (`ENCRYPT`, `DECRYPT`, `HASH`, `ORA_HASH`) выносятся
из ядра в отдельный опциональный пакет `H2Sharp.Crypto`. В ядре не остаётся
криптографических реализаций и обязательной crypto-зависимости; кому нужно —
подключает пакет. SQL-грамматика и регистрация функций идут через общий
механизм .NET UDF из [ADR-001](ADR_DOTNET_EXTENSIONS.md).

Реализация: `H2Sharp.Crypto.UseCrypto()` регистрирует `ENCRYPT`/`DECRYPT`
(AES/XTEA/FOG). По последующим решениям `HASH` остаётся в ядре (BCL/CryptoHives),
а `ORA_HASH` — в `H2Sharp.JavaLegacy`; это уточняет исходный список, не отменяя
принцип «ядро без обязательной crypto-зависимости».

Отсутствие пакета даёт явную ошибку функции/провайдера, а не другой digest или
молчаливое значение. Исходные conformance-тесты сохраняются как перечень
отложенной работы и не удаляются/не фильтруются без отдельной визы.

### D-023. Блокировка Session — reentrant Monitor вместо ReentrantLock

Утверждено пользователем при разборе native TestSequence: `Утверждаю Monitor`.
Существующие Session.Lock/Unlock/IsLockedByCurrentThread используют отдельный
Monitor (Enter/Exit/IsEntered), сохраняя reentrancy и владение потоком
эталонного `java.util.concurrent.locks.ReentrantLock`. Прежний счётчик,
не удерживавший блокировку между вызовами, удалён. SQL/metadata lifecycle
sequence flush переносится из H2 2.5 без замены правил транзакции и cache margin.

### D-024. org.h2.util.Task называется H2Task

Указание пользователя при переносе native Task lifecycle: `Переимнуй класс в H2Task`.
Имя `H2Sharp.Util.Task` конфликтует с `System.Threading.Tasks.Task` в коде и
тестах, импортирующих оба namespace. Класс называется `H2Sharp.Util.H2Task`;
Call/Run/Execute/Get/GetException/Join/IsFinished и stop-lifecycle сохраняют
эталонную структуру. Старые тесты не требуют дополнительных alias.

### D-025. Именованные параметры ADO.NET — `$name`

Утверждено пользователем при обсуждении `h2-named-parameters-design.md`.
Именованный параметр ADO.NET пишется `$name`; слой команд переписывает его в
эталонный индексированный `$N` до `PrepareCommand`. Движок, токенайзер, парсер
и `Prepared` не меняются, поэтому `$N` остаётся поведением H2 2.5, а `$name` —
расширением ADO-слоя.

`@name` — сессионная переменная H2, `:name` — обычный синтаксис; параметрами они
больше не считаются. Это осознанный breaking change. Имена `$name`
регистрозависимы; `H2ParameterCollection.IndexOf` и родственные методы тоже
сравнивают имена через `Ordinal`, иначе при `$id` и `$Id` нельзя выбрать индекс.
Отсутствующий `$name` — ошибка, смешивание с `?`/`?N`/`$N` — ошибка. Dapper
2.1.66 понимает `$` в `FilterParameters`/`GetInListRegex`; EF Core и linq2db
провайдеры генерируют `$` в SQL.

### D-026. Шифрование SQL-скриптов (`SCRIPT ... CIPHER`) — вне scope

Указание пользователя от 2026-10-27: **«чипер не надо»**. Это относится к
шифрованию логического SQL-дампа: `SCRIPT ... CIPHER AES PASSWORD ...` и
`ScriptCommand` cipher не портируются. Тесты `Cipher_Aes_IsAcceptedByScript`
и `ScriptEncryption_Aes_IsAccepted` остаются в наборе как `BlockedByPort` и
не удаляются.

Решение не отменяет SQL-функции `ENCRYPT`/`DECRYPT` в `H2Sharp.Crypto` и
`HASH` в ядре: это другой слой. `SCRIPT TO`, `CHARSET` и `COMPRESSION`
по-прежнему в работе; отсутствие cipher не является основанием сузить
остальные опции.

### D-027. Команда `HELP` — вне scope

Указание пользователя от 2026-10-27: **«хелп тоже не надо»**. SQL-команда
`HELP [anything ...]`, встроенный `org/h2/res/help.csv` и его CSV-читатель
не портируются. Тест `Help_WithTopic_ReturnsHelpRows` остаётся в наборе как
`BlockedByPort`.

Заглушка, возвращающая пустой или выдуманный список тем, не вводится: это
выглядело бы как поддержка, которой нет. D-005 (CSV/FILE-функции) это решение
не расширяет.

### D-028. Команда `RUNSCRIPT` — вне scope

Указание пользователя от 2026-10-27: **«вообще ранскрипт нафиг»**. SQL-команда
`RUNSCRIPT FROM ...`, её `CHARSET`/`QUIRKS_MODE`/compression-опции и чтение
SQL-скрипта из файла не портируются. Тесты `RunscriptCommandTests` остаются
в наборе как `BlockedByPort` и не удаляются.

Это не отменяет `SCRIPT TO` и остальные опции `SCRIPT`: генерация SQL-дампа
и его выполнение — разные команды. Заглушка, которая делает вид, что файл
выполнен, не вводится.

### D-029. `MODE` фиксируется при открытии

Указание пользователя: режим задаётся до открытия базы и не переключается.
`SET MODE` с тем же режимом — no-op; с другим — `FEATURE_NOT_SUPPORTED_1`.
Второй connection к тому же storage с другим `MODE` получает
`DATABASE_ALREADY_OPEN_1`; после закрытия последнего connection storage можно
открыть с другим режимом. `MODE` не персистится.

### D-030. Linked tables вне core scope

`CREATE LINKED TABLE` и `LINK_SCHEMA` не портируются в core: это мост к
внешнему JDBC/ADO.NET provider-у, а не часть встраиваемого storage engine.
Тесты остаются в наборе как `BlockedByPort`, не удаляются. Пересмотр — только
отдельным опциональным пакетом.

### D-031. Публичная строка подключения — classic ADO.NET

`H2Connection` принимает только classic `Data Source=...;Storage=File|Memory;
Mode=...`. `jdbc:h2:` в публичном API отвергается. Синтаксис разбирает
`DbConnectionStringBuilder`; `ConnectionInfo` — typed DTO без разбора строк.
JDBC URL остаётся только в тестовой инфраструктуре для Java-оракулов.
`Driver.Connect`/`AcceptsURL` и JDBC URL constants удалены; `Driver` оставлен
только для регистрации `DbProviderFactory`.

## B. Кандидаты (НЕ утверждено — код с такой пометкой остаётся дефектом)

### P-007. `ROWNUM` в DML — текущей команды нет

Поля `currentSelect`/`currentPrepared` заведены, и `ROWNUM` читает
`aggregateSelect ?? currentSelect ?? currentPrepared`, как
`getCurrentPreparedOrSelect`. Остаток: parse-only слой DML (`INSERT ... VALUES`,
`UPDATE ... SET`) строит запись команды без `Prepared`, поэтому `ROWNUM`
там бросает `TODOException` с именем недостающего. В эталоне это работает.
Дописать, когда parse-only слой будет создавать команду до чтения выражений.

### P-008. `DbSettings` (таблица h2.*-свойств) не портирована

`INFORMATION_SCHEMA.SETTINGS` показывает только именованные настройки.
Открыто: реализовывать таблицу или фиксировать отсутствие.

### P-009. Read-only база берётся эксклюзивно

Эталон для `FILE_LOCK=FS` берёт `fileChannel.tryLock(0, MAX, readOnly)`: shared для
read-only и exclusive для read-write, поэтому несколько процессов могут открыть
одну базу только на чтение. В .NET `FileStream.Lock` умеет только exclusive, а
`FileShare.None` — единственный режим, который runtime проверяет на Unix. Поэтому
порт берёт exclusive-лок и для read-only: второй read-only процесс (и порт, и
эталон) получает `DATABASE_ALREADY_OPEN_1`. Данные не портятся, но параллельное
чтение из нескольких процессов невозможно. Пересмотр — вместе с shared-локом
(P/Invoke `LockFileEx`/`fcntl` или новый BCL API). На macOS `FileStream.Lock`
не реализован, и `FileChannel.TryLock` бросает `TODOException` с именем
недостающего (файловая БД там пока не открывается) — это дефект порта.

## C. Дословные копии, вопросов не требуют

* `ESTIMATED_ENVELOPE` и пропущенные kinds (`DOMAIN`, `CONSTANT`, `ROUTINE`,
  `SYNONYM`, `TRIGGER`, `ROLE`, `USER`) отвечают `NULL` — ровно то, что
  эталон отвечает при пустом поиске. Дописать ветви, когда появятся сами
  объекты (spatial-индексы, домены и т.д.); пометка стоит в коде.
* `GetDiskSpaceUsed`: `Index`/`Table` → 0, `MVTable` — сумма/primary,
  `MVIndex` — корень мапы (как в эталоне).
* `readIfWords` — пик со сдвигом, кавычки не совпадают (как `testToken`).
* `SupportsPrecision` для `TRUNCATE_VALUE` — `{NUMERIC, DECFLOAT, ARRAY}`.
